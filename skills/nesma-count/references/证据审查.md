# 证据审查

证据审查是在正式计数前建立事实底账，不是预估功能点。

## 证据角色

每条证据登记为以下一种或多种角色：

- 意图：目标、范围、变更授权；
- 现状：现行流程、用户资料、旧系统行为；
- 规格：PRD、用例、验收准则；
- 实现：代码、数据结构、接口、批处理；
- 验证：测试、运行观察；
- 用户确认：用户对计数分叉的明确答复。

派生材料必须有可追溯的原始来源；不可追溯的派生材料只能发现候选，不能独立支撑正式计数。用户确认是有效证据，但必须记录问题、答复和时间，不能写成无来源的假设。

## 基线

- 每个 Git 证据仓库固定到 commit；tag 或分支先解析为 commit。
- 当前工作区中的未提交文件默认不作为证据；用户明确指定时记录原因。
- 只读采集不得改变业务数据、会话、任务、缓存或其他状态。
- 发现会改变已确认边界、范围、用户或方法的矛盾时，返回启动确认，不继续计数。

## 候选清单

从证据中建立：

- 数据功能候选：逻辑数据组、维护责任、ILF/ELF、RET、DET；
- 事务功能候选：基本过程、EI/EO/EQ、FTR、带侧 DET；
- 非计数项：非功能需求、技术任务、排除范围；
- 未决队列：证据仍有一种以上合法读法的项目。

页面、菜单、API、数据库表和代码函数只能作为发现候选的线索，不能直接决定功能类型或数量。

## 正式行门槛

正式行必须有以下证据：

- 功能存在且用户可识别；
- 维护责任和应用边界明确；
- 基本过程或逻辑文件边界明确；
- 类型和复杂度要素足以复算；
- 每个正式行至少引用一条有效证据；
- 有用户确认记录，或证据本身已唯一决定判断。

未解决的项目不进入正式行。先批量问用户；用户无法回答时，写入 `excluded`，说明排除理由和对 UFP 的影响。不要生成“阻断包”，也不要保留假设。
