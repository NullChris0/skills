# 交付模型契约

阶段二保留一个内部 `delivery-model.json`，把阶段一 JSON、代码证据、接口 YAML、图片和 Word 章节连接起来。该文件不是客户输入，也不是第二套计数事实；它是 document builder 的结构输入，必须随本轮产物保留用于校验。

## 顶层

```json
{
  "model": {},
  "specs": [],
  "dbs": [],
  "masters": [],
  "features": [],
  "mappings": [],
  "document": {}
}
```

- `model`：阶段一计数模型的只读副本或引用。
- `specs`：HTTP 接口和跨边界只读契约。
- `dbs`：物理表补充信息。
- `masters`：边界外主数据读取契约。
- `features`：功能清单行。
- `mappings`：NESMA 覆盖映射。
- `document`：Word 章节、段落、表格、图片和图题。

## 文档

`document` 至少包含：

- `title`、`subtitle`、`version`、`date`；
- `counts`：从阶段一 JSON 复算的 ILF/ELF/EI/EO/EQ/UFP，不手工填写；
- `sections`：按顺序排列的章节；
- `cover`、`header`、`footer` 等样式字段。

章节项至少包含：

```json
{
  "heading": "章节标题",
  "level": 2,
  "paras": ["正文"],
  "images": [{"path": "接口表/images/card.png", "caption": "表号 图题"}],
  "tables": [{"headers": [], "rows": [], "widths": []}]
}
```

上面的标题、图题和表号是形状示例。本次文档不是通用软件工程意义上的标准 SRS，但必须使用联通交付文档骨架，不能退化为任意章节的紧凑说明。所有图片路径使用相对交付目录的路径，不能引用 `/tmp` 或旧接口表目录。所有 NESMA 编号和 UFP 从阶段一 JSON 派生。

必需的一级章节：

`1 项目概述`、`2 文档目的`、`3 文档范围`、`4 术语和缩写解释`、`5 参考文档`、`6 范围定义`、`7 功能需求`、`8 界面需求`、`9 非功能性需求`、`10 其它需求（可选）`。

项目概述必须包含 `1.1 项目背景`、`1.2 系统总体功能结构`、`1.3 往期建设情况`、`1.4 本项目预算工作量`、`1.5 本项目投资计划预算`。功能需求必须包含 `7.1 数据模型` 和 `7.2 界面功能模块`。

每个数据功能必须有独立章节，并包含“需求描述”“数据来源及流向”“加工逻辑”三段正文。每个事务功能必须有独立叶子章节、至少一段正文，以及接口表或规则表。功能清单必须一条事务功能一行。

`card_style` 可选，指向改写后的 `api-card.sty`。相对路径相对交付模型所在目录。缺省时使用 Skill 自带范本。

## 映射

每条映射至少包含：

```json
{
  "id": "TF-01",
  "type": "EI",
  "name": "功能名称",
  "fp": 3,
  "feature_rows": "功能清单行标识",
  "section_page_model": "7.2.x 具体叶子章节；功能清单行标识",
  "interfaces": "YAML id 或空",
  "status": "已覆盖",
  "note": "可选说明"
}
```

映射必须覆盖阶段一 JSON 的全部正式行；没有接口的功能保留空 `interface`，不能为了填满表格虚构接口。

## 生成顺序

1. 读取阶段一 JSON，校验无假设和未决项；
2. 生成映射；
3. 从代码证据生成接口 YAML；
4. 渲染卡片图片；
5. 生成功能清单 XLSX；
6. 生成 `delivery-model.json`；
7. 生成 DOCX；
8. 执行独立校验脚本。
