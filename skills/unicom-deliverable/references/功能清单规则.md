# 功能清单规则

## 列

系统名称、一级模块、二级模块、功能需求描述、外部接口需求描述、功能（新增/修改）。没有序号列和备注列。系统名称整列合并，一级模块按相同值合并。

`rows.json` 是对象数组，每行五个键：

```json
{"module": "新闻文章管理", "name": "文章审核驳回",
 "desc": "对待审核文章执行驳回，文章回到草稿；按作者工号和姓名查找接收人，生成“新闻稿件已驳回”通知，接收人初始为未读。",
 "external": "读取主系统人员信息定位接收人；通知写入主系统通知中心。", "type": "新增"}
```

## 行的两种类型

**数据实体行**：名称以“信息”结尾，如“新闻文章信息”。每个由本系统维护的业务数据对象一行，排在所属一级模块的最前面。描述写成：

> XX信息包括属性一、属性二……。其中A、B为输入项，C、D为选择项；一个X可以有多个Y。

只读别的模块或外部系统数据的模块没有实体行。会话、审计日志等技术支撑数据默认不列；要列先问用户。

**功能行**：一个独立操作一行。新增、删除、修改、列表查询、详情查询、导入、导出、提交、审核通过、驳回、隐藏、取消隐藏各占一行；单条保存和批量保存、同一页面的不同页签列表，只要后端是不同操作也分行。

## 拆分与取舍

- 拆到最细，但只列真实存在且页面实际用到的功能。后端有接口而前端没有任何页面调用的，不列。
- 不为凑数拆分。下拉选项类查询是真实接口时可以列，但要在报告里提示用户：评估方常把它并入主查询。
- 一次性历史数据迁移单独作为最后一个一级模块，按迁移对象分行。是否列入由用户决定。
- 一级模块按业务划分。整张表只有一个一级模块说明粒度太粗，按需求说明书章节或领域文档拆开。

## 命名与描述

- 二级模块名用“对象+动作”的短名词：文章新增、栏目列表查询、文章审核驳回。同一一级模块内不得重名。
- 描述用一两句业务语言。查询类写“输入……，显示……”；维护类写“输入/修改……，校验……，保存后……”；流程类写“对……状态的……执行……，状态改为……”。
- 不写接口路径、表名、权限码、类名、HTTP 方法，不写任何计数编号或功能点数。
- 描述里的每个事实都要能在代码里找到。返回字段没有的东西（“跳过数量”“默认年份”）不写。

## 外部接口需求描述

与本系统之外没有交互就只写“不涉及”。有交互才写一句，点明对方系统：“读取主系统人员信息。”“文件上传至对象存储。”不写本系统自己的接口。

## 新增/修改

按项目定性填。整体重建的系统全部填“新增”，并在说明书 1.3 说明原因。

## 顺序

每个一级模块内：数据实体行 → 增 → 删 → 改 → 查 → 其他（上传、导入导出、提交、审核、状态流转，按业务先后）。

两种情况改用使用流程顺序，即先做的排前面：

- 只有查询的模块。
- 有明确先后步骤的模块，例如先登录、查询，再保存草稿、提交、导出。

## 用户改过之后

用户回填或删改清单后，以磁盘上的 xlsx 为准。再次修改前先读回当前内容，只改用户要求的部分，不把已删的行带回来。
