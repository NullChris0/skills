# 成稿与校验

## 输入

唯一计数输入是阶段一 JSON。旧 Word/PDF、旧功能清单和旧接口表目录不得提供 NESMA 编号、类型、FP 或业务事实。它们只能在用户明确要求时帮助理解版式。

## 映射表

先建立 `映射表.xlsx`，至少包含：

- NESMA 编号、类型、名称、FP；
- 功能清单序号和功能名称；
- 正文章节、页面或数据模型位置；
- 接口 YAML 或卡片 ID；
- 覆盖状态和说明。

每条 NESMA 记录必须有归属；一个功能清单行可以映射多个 NESMA 记录，一个 NESMA 记录可以出现在正文多个位置。不得重复计量。

## 功能清单

使用 `assets/联通功能清单模板.xlsx` 的列顺序：

序号、系统名称、一级模块、二级模块、功能需求描述、外部接口需求描述、功能（新增/修改）、备注。

功能清单一事务功能一行，共 N 行对应阶段一的 N 个事务功能。备注保留该行唯一的正式 NESMA 编号；数据功能在数据模型章节和映射表中体现，不混入事务行。未独立计数的能力只在正文的支撑工作或排除项中描述，不新增编号。连续行的系统名称和共同模块可合并单元格，但不得跨页。

## 接口表

按 [接口表YAML规范.md](接口表YAML规范.md) 生成 YAML。YAML 是编辑面，TeX 卡片和图片是投影：

```text
YAML -> TeX 卡片 -> PNG/SVG 图片 -> Word
```

Word 中为每张接口表保留图位、图题、表号和正文引用。接口表只描述成功契约和代码基线支持的字段，不复制旧交付件中的错误码、示例或路径。

## Word

Word 由 document builder 从 `delivery-model.json` 的 `sections` 直接写出，不用 PDF 转 Word。本稿不是通用软件工程意义上的标准 SRS，但必须按联通交付文档骨架组织，不能退化为任意章节的紧凑说明。

固定一级骨架：

1. 项目概述
2. 文档目的
3. 文档范围
4. 术语和缩写解释
5. 参考文档
6. 范围定义
7. 功能需求
8. 界面需求
9. 非功能性需求
10. 其它需求（可选）

项目概述必须包含项目背景、系统总体功能结构、往期建设情况、本项目预算工作量、本项目投资计划预算。功能需求必须包含数据模型和界面功能模块。

数据模型按业务身份组织，物理表作为补充，不按表数推导数据功能。每个数据功能必须有独立章节，并包含需求描述、数据来源及流向、加工逻辑三段正文。页面按入口、角色、共同数据、状态和叶子功能组织；每个事务功能必须有独立叶子章节、正文以及接口表或规则表，不能只靠一个高层功能清单章节覆盖。调用规则只保留 YAML 中的业务句子。

## 完成校验

```bash
python <skill-directory>/scripts/build_delivery.py <delivery-model.json> <输出目录>
python <skill-directory>/scripts/validate_delivery.py <计数模型.json> <输出目录> [--delivery-model <delivery-model.json>]
```

- JSON 的每个数据功能、事务功能都在映射表中有唯一归属；
- Word 具备完整联通交付骨架，每个数据功能有三段正文，每个事务有独立正文和载体；
- 功能清单严格一事务一行；
- 功能清单没有旧编号、旧 UFP 或未确认假设；
- 接口 YAML 的端点、方法、鉴权和字段有代码证据；
- 每张 YAML 卡片有对应图片，Word 中图片可打开且图题/引用连续；
- Word 中的数据功能数、事务功能数和 UFP 完全来自 JSON，不写死；
- Word 中出现的全部 `N UFP` 必须等于计数模型复算值，全部 DF/TF 编号必须存在于计数模型；
- 数据割接、迁移、环境切换等非计数工作未进入 FP；
- 输出目录只包含本次版本产物，不覆盖旧版本。
