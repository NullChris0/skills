# 需求说明书规则

章节骨架由 `build_requirement_doc.py` 固定，你只写 `spec.json` 的内容。写之前完整读一遍范本，照它每一章的篇幅、口吻和句式写。

## 章节

| 章 | 内容 | spec 字段 |
| --- | --- | --- |
| 封面 | 标题、“需求说明书”、月份 | `title`、`date` |
| 1.1 项目背景 | 业务现状和痛点，然后“具体需求如下：”，每条诉求一段，以“1、”“2、”开头 | `background` |
| 1.2 系统总体功能结构 | 一句引导语、结构图、模块表（一级模块 / 主要功能 / 使用角色） | `structure_intro`、`structure_figure`、`structure_table` |
| 1.3 往期建设情况 | 旧系统情况；整体重建时说明第 8 章因此均为“新增” | `history` |
| 1.4、1.5 预算 | 不填，脚本写“无。” | — |
| 2 文档目的、3 文档范围 | 各一段 | `purpose`、`scope` |
| 4 术语和缩写解释 | 两列表 | `terms` |
| 5 参考文档 | 每条一段 | `references` |
| 6 范围定义 | 本系统负责什么，哪些能力由外部系统提供 | `boundary` |
| 7 系统交互关系 | 首段“涉及系统间交互：”，其后每条以“1、”开头 | `interactions` |
| 8 功能需求 | 8.1 系统 → 8.1.N 一级模块 → 8.1.N.M 功能 | `system_name`、`modules` |
| 9 接口需求 | 只列外部接口，句式“XX查询 - 复用” | `interfaces` |
| 10 界面需求 | 一句引导语加界面截图 | `ui_intro`、`figures` |
| 11 非功能性需求 | 性能、安全、易用性等，每条一段 | `nonfunctional` |
| 12 其它需求 | 默认“无。” | `other` |
| 附录 A 物理表清单 | 物理表图片，可选 | `appendix` |

## 第 8 章

`modules` 的名称、顺序和新增/修改必须与已定稿的功能清单逐行一致，脚本会比对并拒绝不一致的 spec。

```json
{"name": "文章审核驳回", "type": "新增",
 "desc": "新增文章审核驳回服务，审核人员对待审核文章执行驳回，文章回到草稿，拟稿人员可继续编辑。系统按文章作者工号和姓名在主系统人员信息中查找接收人，生成通知写入主系统通知中心；找不到接收人时不生成通知。",
 "input": "文章标识", "output": "操作结果、驳回通知"}
```

- 功能的 `desc` 以“新增XX服务，”开头，在清单描述的基础上扩成两三句：谁在什么场景操作，系统校验什么，结果是什么。不得与清单描述矛盾。
- 功能必须同时有 `input` 和 `output`，写字段的中文业务名，用顿号分隔；没有输入写“无”。
- 数据实体（名称以“信息”结尾）的 `desc` 写成“新增XX信息，涉及属性包含……等。”，不写 `input`、`output`。
- 不写接口路径、表名、权限码、类名。

生成后每条功能在 Word 里是：`修改类型：☑新增 □修改 □删除`、`功能描述：…`、`输入项：…`、`输出项：…`。

## 不能写的

- 功能点数、UFP、人月、TF/DF 编号、工作量分摊算法。“总量先定、再按占比分”这类话等于告诉评审工作量是倒推的。
- 字段表、接口契约表的截图。评估人无法检索图片里的输入输出项；字段写进实体条目和输入项、输出项。
- 没有依据的痛点、旧系统情况和性能承诺。旧材料没写痛点，就只写现状和诉求。
- 自相矛盾的定性：标题叫“改造”而正文说“新开发”；1.3 写“无”而别处又有历史数据迁移。

## 图片

- `structure_figure`：`{"image": 路径}`，放在 1.2 引导语和模块表之间。
- `figures`：界面截图，`{"image", "caption"}`，图题不带图号。挑 10 到 16 张，尽量每个一级模块一张；没有截图的模块不放，并在报告里说明。
- `appendix`：物理表图片，图题用“表N 某某物理表”。

## 与清单保持一致

清单改了任何一行的名称、顺序或新增/修改，都要同步 spec 并重新生成说明书。清单描述因与代码不符而改正时，说明书对应条目一起改。范围定义也跟着清单走：清单列了历史数据迁移，第 6 章就不能再说它在边界外。
